## 資料完整性說明（本期新發現，列入紅色區）

計算指標時發現：Jira 上共 **27 張 Story 進入 DONE**，但 `metrics/events.jsonl`
中只有 **17 張**能找到對應的 `stage_transition → Done` 事件記錄，缺口達
**10 張**（SDLCAIP1-4、14、19、20、23、24、29、34、35、36）。一次通過率的
81.5% 是以 Jira 的 27 張 Done 為分母、`reopen` 事件涵蓋的 5 張（SDLCAIP1-8、
9、10、14、18）為分子扣除算出，**假設**缺口中的 10 張沒有未被記錄的
reopen——這個假設合理但無法 100% 保證。

Story 端到端時間也因此無法可靠計算：Jira 的 `resolutiondate` 欄位在本專案
未被填入（DONE 狀態沒有對應到 Jira 的 resolution 動作），只能退而求其次用
`metrics/events.jsonl` 的 stage_transition 時間戳推算，但同樣受上述缺口影響。

## 紅色區 🔴

## 流程改善建議（本期已落實 vs 待落實）

### 已落實（本次 pilot 期間發現問題並當場修正，寫入 `CLAUDE.md`）

| # | 觀察到的問題 | 落實的規則 |
|---|---|---|
| 1 | Gate report 有時在狀態轉場之前就貼出 | 規則 3b：轉場與貼報告視為一個原子動作 |
| 2 | Context 壓縮恢復後，orchestrator 重用了別的狀態下看到的 transition ID，導致漏轉場 | 規則 3c：貼任何 gate report 前重查當下狀態的 transition |
| 3 | 曾經誤在本機 `main` 上直接 commit | 規則 4b：絕不在本機 main 上 commit |
| 4 | 共用 checkout 中，即使只有單一 subagent（非平行委派），orchestrator 自己的 housekeeping 或第二個唯讀 subagent 仍可能造成資料遺失/誤判 | Delegation rules：訂正原本錯誤的「sequential 不需要 worktree」說法，補上具體案例與規則 |
| 5 | Reviewer 等唯讀 subagent 無法自己 checkout 分支 | Delegation rules：委派前 orchestrator 必須自己先 checkout 目標分支 |
| 6 | 「只改前端/後端某一側」被誤用來跳過完整測試套件，導致跨檔案一致性測試的回歸沒被抓到（SDLCAIP1-31/33 皆發生過） | Delegation rules：不得以檔案範圍為由跳過完整測試套件 |
| 7 | 手動打 `\uXXXX` unicode escape 寫中文進 Jira 曾多次打錯字但不報錯 | Language 段落：優先傳遞原生 UTF-8，必要時寫入後立即回讀確認 |
| 8 | 上述 6 條教訓originally 只存在單一 session 的 persistent memory，未寫進規則，換一個新專案/模板就會遺失 | 規則 9（元規則）：教訓必須提升成 git-tracked 規則，memory 只能是輔助 |

這 8 條在 `CLAUDE.md` 裡都能查到對應規則與案例說明，不在此重複細節。

### 待落實（本次回顧新發現，建議下次啟用新專案前處理）

1. **Metrics 事件與 Jira 狀態的一致性沒有自動交叉驗證機制**（見紅色區）——
   建議在 `docs/07` 補一條：reporter 週回顧時，除了聚合 events.jsonl，也應該
   反查 Jira 目前 DONE 的工單清單，找出兩邊對不上的工單並列入紅色區，而不是
   假設 events.jsonl 完整。
2. **CI 的 `--screenshot=on` 截圖偶爾不完全反映真實渲染結果**（SDLCAIP1-34
   驗收時發現一次：舊截圖看起來標題未置中，重跑同一個 commit 的 CI 後截圖
   正確，程式碼本身經真實瀏覽器驗證是對的）——目前判斷是一次性偶發狀況，
   建議如果之後再遇到同類情況，優先重跑 CI 而非急著開修正票，但若重複出現
   則要認真排查是不是 CI runner 的通用問題。
3. **Story 端到端時間目前無法從 Jira 或 events.jsonl 可靠算出**（見上）——
   建議之後要嘛在 Jira workflow 設定讓 DONE 狀態觸發 resolution 動作，要嘛
   由 reporter 直接讀 Jira changelog 計算，不要依賴容易有缺口的
   events.jsonl 時間戳。

## Auto gate 進度評估（對照 docs/06 §5）

docs/06 §5 的推進條件是「連續放行次數」，不是行事曆週數。實際核對
`metrics/events.jsonl` 的時間序：

- **G1**：唯一一次駁回是 SDLCAIP1-8（2026-08-11），此後連續 **15 次**核准、
  零駁回，**已超過「連續 10 次無駁回 → G1 轉 auto」的門檻**。
- **G2**：全程 **21 次核准、0 次駁回**，**已超過「連續 20 次無駁回 → G2 轉
  auto」的門檻**。
- **G1b**（architecture 模組自帶的 gate）：唯一一次駁回是 SDLCAIP1-9
  （2026-08-11），此後連續 **16 次**核准、零駁回，數字上同樣亮眼，但
  docs/06 §5 目前**只明訂了核心 G1/G2 的 auto 轉換路徑，沒有規範模組自帶
  gate（如 G1b）的 auto 轉換條件**——這是文件的一個空白，若要讓 G1b 也走
  auto，需要人類先決定並補一條規則，不能直接套用核心 G1 的門檻。

**重要提醒（人類決策時要考慮的變因）**：以上數字全部發生在同一段約 12 天
高密度 pilot 期間，不是分散在自然的多週節奏中累積的——`docs/07` §4 原本設想
的「連續 4 週達標」隱含的是**跨時間、跨情境的穩定性驗證**，這次因為 pilot
本身密集執行，實際上是壓縮在一個短時間窗完成的。數字上確實達標，但你身為
人類監督者這段期間對每個 gate 都保持高度專注審查，這種專注力本身可能是
低駁回率的一部分原因——換成真正常態、較低頻率地看板的情境下是否還能維持
同樣的核准品質，本次 pilot 的資料無法回答。**建議**：如果要推進 auto gate，
可以考慮，但不必因為數字達標就照單全收；也可以選擇先維持 manual 一段時間，
看看在正常、非密集節奏下駁回率是否仍然一樣低，再做決定。這個決定權在你，
`config/gates.yaml` 是人類專屬檔案。

## 定性總結：框架驗證了什麼

- **Agent 角色分工**：requirements-analyst / architect / developer / tester /
  reviewer 的職責邊界在 27 張 Story 的實際執行中沒有出現混亂或越權，
  reviewer 的唯讀限制、tester 的獨立測試視角都如設計所預期發揮作用。
- **模組系統可用**：architecture 模組（G1b + Designing 階段）從無到有實際
  用起來，成功攔下至少一次「規格與現況程式碼不符」的問題（SDLCAIP1-35 的
  `.pagination` 間距映射錯誤）。
- **HUMAN-INPUT / Blocked 機制運作正常**：8 次人工介入中，多次是 agent
  正確判斷「不可自行假設」而主動停下來問人類（SDLCAIP1-16 的 6 項架構決策、
  SDLCAIP1-32 的刪除互動範圍問題等），沒有出現自行猜測需求的情況。
- **升級機制全程未觸發**：0 次 escalation_used，代表 Sonnet 級模型足以應付
  這個規模專案的所有階段，沒有需要動用高階模型配額的情況。
- **CONSTITUTION.md + design-system.md 的判斷收斂機制有效**：後續 6 張 UI
  套用 Story（SDLCAIP1-31~36）在有了明確的視覺規範文件後，沒有再出現前幾張
  Story 常見的「架構層級待決問題」類型 HUMAN-INPUT，判斷收斂的設計目的達成。
- **最大的脆弱點是共用 git checkout**：這次 pilot 幾次最嚴重的問題（資料
  遺失、reviewer 審到錯誤分支、metrics 事件缺口）根源都指向同一件事——
  orchestrator 與 subagent 共用同一個工作目錄。已經寫成規則但仍值得未來
  優先考慮：是否讓 orchestrator 預設對所有委派（不只平行委派）都用獨立
  worktree，徹底消除這類 race 的可能性，而不是靠規則要求 agent 每次自律
  避開。

## 給下一個專案（若拿這個當模板）的建議

- `CLAUDE.md`、`docs/*`、`templates/*`、`config/gates.yaml` 結構、
  `modules/architecture/` 這些框架層檔案可以直接沿用，這次的教訓都已經
  寫進去了。
- `CONSTITUTION.md`、`docs/design-system.md`、`docs/design/*.md`、
  `project-profile.yaml`、`docs/PRD.md` 是這個專案的專屬內容，套模板時要清掉
  或整份替換。
- 建議新專案一開始就把「orchestrator 預設用獨立 worktree」這個待落實建議
  一併考慮進去，不用重新踩一次共用 checkout 的坑。
